## 1. 프로젝트 소개

**옷 사이즈 비교 서비스**는 내가 이미 가진 옷의 실측 치수를 기준으로, 온라인에서 사려는 옷의 기재 치수를 항목별로 비교해 구매 전 사이즈 실패를 줄여주는 웹 서비스입니다. 같은 "M" 사이즈라도 쇼핑몰마다 실측이 다르기 때문에, 잘 맞는 내 옷을 기준점으로 삼아 총장·어깨·가슴 등을 직접 비교할 수 있게 했습니다. cm·인치 단위 변환을 지원합니다.

직접 겪은 문제를 정의하고, 기획부터 개발·배포까지 **1인 풀스택**으로 구현한 프로젝트입니다.

## 2. 문제 정의

### 해결하고 싶은 문제

온라인 의류 구매의 주요 반품 사유는 사이즈 불일치입니다.

- 같은 "M"이라도 쇼핑몰마다 실측 치수가 다르다.
- 상세페이지의 숫자만으로는 내 몸에 맞을지 감이 안 온다.
- 잘 맞는 내 옷과 사려는 옷을 항목별로 비교할 방법이 없다.

### 대상 사용자

- 온라인 의류를 자주 구매하고 사이즈 실패 경험이 있는 사용자
- 반품 없이 한 번에 맞는 옷을 고르고 싶은 사용자

### 기대 효과

잘 맞는 내 옷을 기준으로 사려는 옷의 치수 차이를 한눈에 확인해, 구매 전 사이즈 의사결정을 돕습니다.

## 3. MVP 범위

### 핵심 기능 4개

1. 회원가입 / 로그인 (JWT 인증)
2. 내 옷장 등록 (상세 치수 + 사진)
3. 위시 상품 등록 (쇼핑몰 기재 치수)
4. 사이즈 비교 (항목별 차이 계산, cm↔인치 변환)

### 이번 MVP에서 제외한 기능

- 쇼핑몰 리뷰 크롤링 (약관·안정성 리스크)
- 사이즈 추천 모델 (데이터 누적 후 검토)
- CI/CD, 모니터링, 배치 자동화 (인프라 심화는 별도 프로젝트에서 담당)

### MVP 원칙

기능을 넓게 벌리기보다, **실제로 동작하고 배포 가능한 서비스**를 우선했습니다. 인프라 심화 요소는 별도 프로젝트에 두고, 이 프로젝트는 파이썬 기반의 기획→개발→배포 완결에 집중했습니다.

## 4. 주요 기능

### 4.1 회원가입 / 로그인

이메일·비밀번호로 가입하며, 비밀번호는 bcrypt로 해싱해 저장합니다. 로그인 성공 시 JWT 토큰을 발급하고, 이후 요청은 토큰으로 인증합니다. 모든 데이터는 `user_id` 기준으로 격리되어 본인 데이터만 접근할 수 있습니다.

### 4.2 내 옷장 등록

잘 맞는 옷의 상세 치수(총장·어깨·가슴·소매·허리·엉덩이)와 사진 한 장을 등록합니다. 사진은 AWS S3에 저장하고, DB에는 객체 키(photo_key)만 저장합니다.

### 4.3 위시 상품 등록

사려는 옷의 쇼핑몰 기재 치수를 입력합니다. 옷장과 동일한 구조로, 카테고리와 치수를 저장합니다.

### 4.4 사이즈 비교

내 옷과 위시 상품을 선택하면 치수를 항목별로 비교합니다.

- 항목별 차이값 계산 ("내 옷보다 +2cm" 형태)
- cm↔인치 단위 정규화
- 누락된 치수 항목은 에러 없이 예외 처리
- 카테고리가 다르면 비교 불가 안내

- Python

## 6. 서비스 아키텍처

```
사용자(브라우저)
      │
      ▼
   Nginx  ── "/"    정적 프론트 서빙
      │    ── "/api" 리버스 프록시
      ▼
  FastAPI (백엔드)
      │
      ├──▶ MySQL (사용자·옷·위시 정형 데이터)
      └──▶ AWS S3 (사진 비정형 데이터, presigned URL)
```

- 프론트/백엔드를 REST로 분리하고, 정형(MySQL)·비정형(S3) 저장을 분리했습니다.
- 구성 요소별로 컨테이너를 나눠 Docker Compose로 오케스트레이션했습니다.
- S3 버킷은 퍼블릭 접근을 차단하고, 조회 시 10분 유효 presigned URL을 발급해 안전하게 사진을 제공합니다.

## 7. API 명세 (핵심)

### 7.1 회원가입

```
POST /api/auth/signup
```

```json
{ "email": "user@example.com", "password": "string" }
```

### 7.2 사이즈 비교

```
GET /api/compare?garment_id={id}&wishlist_id={id}&unit=cm
```

응답 예시:

```json
{
  "unit": "cm",
  "my_garment_name": "내 청바지",
  "wish_item_name": "쇼핑몰 청바지",
  "items": [
    {
      "field": "waist",
      "my_cloth": 35,
      "wish_cloth": 37,
      "diff": 2,
      "message": "내 옷보다 +2cm 큽니다",
      "comparable": true
    }
  ],
  "compared_count": 1,
  "missing_count": 0
}
```

### 7.3 사진 업로드

```
POST /api/garments/{garment_id}/photo   (multipart/form-data)
```

전체 API 명세는 서버 실행 후 Swagger(`/api/docs`)에서 확인할 수 있습니다.

## 8. 로컬 실행법

```bash
git clone https://github.com/jsemii/size-compare-web-service.git
cd size-compare-web-service

# backend/.env 에 DB·JWT·AWS 자격증명 설정 (커밋 금지)

docker compose up -d --build                       # 백엔드·MySQL·Nginx 기동
docker compose exec backend python init_db.py      # 테이블 생성
```

브라우저에서 `http://localhost` 접속.

## 9. AI 코딩 에이전트 활용 방식

이 프로젝트는 AI 코딩 에이전트를 단순 코드 생성기가 아니라, **개념을 먼저 이해하고 직접 구현한 뒤 리뷰받는 학습 파트너**로 활용했습니다.

### 작업 흐름

```
개념 설명 요청
→ 직접 코드 작성
→ 리뷰 및 오류 수정 (에러는 항상 맨 아래 줄부터 함께 해석)
→ 커밋 및 개발로그·트러블슈팅 기록
```

코드를 그대로 받기보다 각 단계의 원리를 이해하고 한 줄씩 직접 작성하는 방식으로 진행해, 전체 스택을 스스로 설명할 수 있는 수준을 목표로 했습니다.

## 10. 트러블슈팅

개발 중 발생한 문제와 해결 과정은 [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)에 정리했습니다. 대표 사례:

- **os.getenv가 `.env`를 자동으로 읽지 않음** → pydantic-settings 기반 config로 통일
- **Docker 컨테이너와 로컬 uvicorn의 8000 포트 충돌** → 코드가 맞는데 반영 안 될 땐 `lsof`로 포트 점유 확인
- **새 노트북에서 테이블 부재** → DB는 git 동기화 대상이 아니므로 머신마다 init_db 재실행

## 11. 회고

### 잘 된 점

- 직접 겪은 문제에서 출발해 MVP 범위를 작게 잡고 끝까지 완성했습니다.
- 기획→개발→AWS 배포까지 1인 풀스택으로 관통했습니다.
- 여러 프로젝트를 병행하며 각 프로젝트의 역할을 의도적으로 분리했습니다. (인프라 심화는 별도 프로젝트, 이 프로젝트는 파이썬 풀스택 완결)
- 맥북·WSL 두 환경을 병행하며 "코드는 git, DB·환경은 머신별 관리"라는 배포 감각을 익혔습니다.

### 배운 점

- `.env`·설정 로딩, 컨테이너 포트, 스키마 동기화처럼 코드 밖의 문제가 실제 배포에서 더 자주 발목을 잡았습니다.
- 서비스는 코드만으로 완성되지 않고 배포·환경·데이터 정합성까지 함께 관리해야 합니다.
- 범위를 스스로 판단해 줄이는 것도 완성을 위한 중요한 결정이라는 것을 배웠습니다.

### 향후 개선 방향

- 위시 상품에도 사진 등록 확장
- 카테고리별 동적 입력 폼 (선택 시 해당 치수 칸만 표시)
- 도메인 연결 및 HTTPS 적용
